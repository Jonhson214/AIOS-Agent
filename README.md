## 📖 项目背景 (Background)

### 1. 数字化现状：海量投入与“数据沉睡”

在企业数字化转型进程中，尽管全球范围内对业务系统（如 ERP、MES、QMS 等）的投入巨大，积累了海量的底层生产与管理数据，但一个残酷的现实是：**超过 73% 的企业数据处于“沉睡”状态。**

这些数据堆积在孤立的业务系统中，未能有效转化为决策支持。目前，核心业务决策依然高度依赖传统的“专家经验（经验法则）”，数据作为核心生产要素的价值远未被释放。

### 2. 核心挑战 (Core Challenges)

为了实现从“经验驱动”到“数据驱动”的跨越，我们必须解决制约智能化决策的三大技术瓶颈：

- **数据孤岛与融合成本：** 企业内部系统（ERP, MES, QMS 等）相互割裂，底层数据体系与标准不统一，导致跨系统的数据打通与融合分析面临极高的开发与维护成本。
- **语义混乱与标准缺失：** 不同业务线对同一物理实体的描述存在严重分歧。例如，在**锂电池制造**场景中，同一电芯的“电压”或“电流”属性在不同系统中命名迥异，这种语义不一致性直接阻碍了数据的深度挖掘。
- **时效滞后与处理瓶颈：** 传统的 **T+1 离线处理模式**存在严重的生产滞后，无法满足现代工业中“秒级”甚至“毫秒级”的实时决策需求。数据往往处于“被动查看”状态，无法主动参与实时决策闭环。

## 🚀 破局之道 (The Solution)

随着 AI Agent 的全面崛起，企业智能化转型对数据的要求正经历从**“看得懂”**、**“用得上”**到**“自主执行”**的历史性跨越。为了彻底解决传统数据架构中的痛点，本产品打造了一套面向未来的企业智能决策平台，核心破局策略如下：

- **统一语义屏障，消除“人机鸿沟”** 重构数据表达方式，彻底解决业务侧与数据侧“人说人话，机器说机器话”的脱节问题。通过统一的数据语义体系，让复杂的底层数据拥有清晰的业务含义，大幅降低跨系统融合与沟通的成本。
- **毫秒级实时处理，激活数据主动性** 突破传统“T+1”的计算瓶颈。无论面对静态数据仓库、流式数据输入，还是高并发的实时数据下发，系统均能实现**毫秒级（ms）**的处理响应。让数据摆脱被动查询的宿命，转变为能够主动响应业务需求的新鲜血液。
- **原生赋能 AI Agent，复刻“专家经验”** 产品底层原生支持 AI Agent 接入，能够系统化地学习和沉淀行业“老师傅”的宝贵经验。当实时数据涌入时，系统可做到毫秒级响应并主动输出智能决策建议，真正将“被动沉睡的数据”转化为“主动创造的价值”。
- **构建“本体”架构，夯实自主决策基石** 引入**本体（Ontology）架构**作为连接“数据世界”与“业务世界”的核心桥梁。这一架构不仅是数据的结构化骨架，更是支撑 AI Agent 理解业务逻辑、实现高度自主决策的关键基础设施。

### 🛠️ 核心实施路径：三层数据本体构建框架

为了实现从底层数据到高层智能决策的跨越，我们设计了“本体定义 - 关系提取 - 本体注入”三步走的标准化构建流程。这一流程完美映射了我们的三层本体架构，是系统真正具备理解和决策能力的基础。

#### 1. 本体定义 (Ontology Definition) —— 构筑统一语义基座

- **核心目标：** 消除语义分歧，打破数据孤岛，实现“书同文，车同轨”。
- **构建内容：** 面向企业中繁杂的业务系统（如 ERP、MES、QMS 等），提取并抽象核心业务实体。通过构建一套标准化的**企业级业务词典**，将不同系统中命名各异、口径不一的底层字段，统一“翻译”并映射到标准本体对象上。
- **解决痛点：** 彻底消除人与人、人与机器、机器与机器之间的语义鸿沟。在这个阶段，离散的沉睡数据被赋予了明确的业务含义，为后续的融合计算扫清了障碍。

#### 2. 关系提取 (Relationship Extraction) —— 沉淀专家经验与业务规则

- **核心目标：** 将隐性的业务逻辑显性化，让机器“学会”老师傅的经验。
- **构建内容：** 数据本身只是孤立的点，真正的价值在于点与点之间的连线。在这一阶段，我们深度剖析核心业务流，提取前一阶段定义的本体对象之间的逻辑与因果关系。更重要的是，我们将行业专家的“Know-How”和经验法则，转化为机器可读的规则与关联属性，交织成一张严密的**业务关系网络（知识图谱）**。
- **解决痛点：** 解决数据“建得好却用不起来”的窘境。通过固化业务理解和经验价值，让系统不仅知道“这是什么”，更知道“它们之间有什么相互影响”，为自主决策提供逻辑推演的轨道。

#### 3. 本体注入 (Ontology Injection/Population) —— 激活 AI Agent 的动态引擎

- **核心目标：** 赋予本体框架生命力，实现毫秒级的数据驱动与主动决策。
- **构建内容：** 静态的本体和规则网络搭建完成后，需要通过本体注入将真实的、流动的业务数据（无论是数仓批数据还是毫秒级的实时流数据）实例化并灌注到本体框架中。这一过程让抽象的框架拥有了实时感知业务状态的能力。
- **赋能决策：** 注入了鲜活数据的本体，成为了大模型和 AI Agent 理解业务世界的“数字孪生”底座。基于前两层构建的语义理解和关系逻辑，AI Agent 可以实时穿梭于数据网络中，自主进行态势感知与逻辑推理，最终输出毫秒级的主动决策建议，完成从“被动看数据”到“主动用数据创造价值”的终极闭环。

## 🏗️ 产品技术架构 (Technical Architecture)

为了将“数据驱动智能决策”的理念真正落地，我们设计了一套端到端的三层技术架构。该架构自下而上层层递进，从底层的数据连接到核心的本体构建，最终支撑上层的智能应用与低代码开发，形成完整的业务闭环：

### 1. 底层：数据连接与执行基座 (Data & Execution Layer)

- **架构组成：** 涵盖**数据源**（工业传感器、数据库、生产日志）、**逻辑源**（计算规则、逻辑引擎、算法模型）以及**业务执行系统**（工业控制系统、现场执行设备）。
- **核心价值：** 作为整个架构的数字神经末梢，它负责泛在连接企业内各种割裂的业务系统和物理设备。其首要任务是将海量、多源的原始数据进行提取和汇聚，并转化为一套人机无歧义的标准数据语言，为上层提供纯净、统一的底层供血。

### 2. 核心层：本体引擎 (Ontology Core)

- **架构组成：** 包含统一工业数据模型、实体关系映射、工业知识图谱、语义统一管理等核心模块。
- **核心价值：** 这是整个智能决策平台的“大脑”与中枢神经。它负责将底层汇聚的数据进行语义统一和关系映射。更重要的是，它将行业专家（“老师傅”）的隐性业务逻辑和宝贵经验，深度融合进**工业知识图谱**中。这一层让冰冷的数据真正拥有了业务关联和经验壁垒，成为机器可理解的知识库。

### 3. 上层：智能应用开发 (Application)

- **架构组成：** 包含分析与工作流、自动化引擎、产品与开发工具三个核心矩阵。
- **核心价值：** 基于核心层准备就绪的“业务大脑”，本层负责将数据价值彻底释放并转化为生产力：
  - **分析与编排：** 提供动态的数据分析看板与业务流程的可视化编排。
  - **AI Agent 自动化：** 引入 AI Agent 智能体，能够基于本体关系进行自主决策，实现工业调度优化、RPA 流程执行以及生产异常的自动化闭环处置。
  - **敏捷开发生态：** 提供开箱即用的 AI 开发平台与**低代码工具**（如本体编辑器）。

### 💡 个人总结与感悟 (Personal Reflections)

回顾这近十个月的开发历程，如果说代码库的膨胀是项目的“物理生长”，那么我个人技术认知的几次重构，才是这段旅程最宝贵的“化学反应”。

起初，我以为大模型落地的瓶颈在于“信息检索不够准”，于是我一头扎进了 RAG 优化的泥潭，死磕各种 Chunking 策略、Reranker 和混合检索；后来，我认为瓶颈在于系统的“被动响应”，于是我将目光转向 Agent，引入 LangChain 和 AutoGen 构建多智能体，赋予系统自主调用工具、执行 NL2SQL 和生成图表的能力。

然而，当多智能体、多模态（Milvus+图谱）和各种复杂工具被强行缝合在同一个系统里时，我撞上了一堵真正的叹息之墙：系统虽然全能，但变得极其脆弱且难以维护。智能体之间缺乏统一的业务认知，常常在复杂的逻辑推理中“各自为政”。

这就引出了我这十个月来最大的一次顿悟：**AI 复杂应用的天花板，往往不取决于你用了多么炫酷的框架，而是取决于底层数据的逻辑表达。**

引入“数据本体建模（Ontology Modeling）”是我补齐的最后一块、也是最重要的一块拼图。它让我从一个“疲于追赶新框架的 API 调用工程师”，蜕变成了一个“思考如何让 AI 真正理解业务底层逻辑的架构师”。当数据本体的底座搭建完毕后，我发现之前写的 NL2SQL Agent、多模态 RAG 突然有了统一的“世界观”和“语言”，它们不再是散落的工具，而是像精密齿轮一样完美咬合在了一起。

在这个技术飞速迭代的时代，今天的流行框架明天可能就会被淘汰。但对数据本质的洞察力、对复杂业务逻辑的抽象建模能力，才是能够穿越技术周期的核心壁垒。从 2025 年 6 月的第一行 Naive RAG 代码，到今天基于数据本体的超级智能体，这段硬核的升级打怪之旅，无比值得。

## 快速开始

### 环境要求

- **Node.js** 18 及以上（与仓库说明一致）
- **npm** 建议使用 **7+**（以便自动处理 `peerDependencies`：本项目为 `react@18.3.1`、`react-dom@18.3.1`）

### 安装依赖并启动主控制台

主前端在 `frontend/` 目录（Vite + React）：

```
cd frontend
npm install
npm run dev
```

浏览器访问终端里 Vite 提示的地址（一般为 `http://localhost:5173`）。

若安装时出现 peer dependency 相关告警或运行缺包，可显式安装与 `package.json` 一致的 React 版本

```
npm install react@18.3.1 react-dom@18.3.1
```

### 生产构建

```
cd frontend
npm run build
```

构建产物在 `frontend/dist/`。

### 配置后端 API（可选）

对接三套能力前，在 `frontend/` 下参考 `frontend/.env.example` 创建 `.env` 或 `.env.local`，例如：

```
cd frontend/graphrag-agent
npm install
npm run dev
```

（`agent-team`、`nl2sql-agent` 同理。）
